# Algorithms and data structures

## Atomic balance and ledger

A movement reads the current balance, computes the new balance, updates `items.quantity`, and inserts the ledger row, all inside one `BEGIN IMMEDIATE` transaction. SQLite grants the reserved write lock before the read, so two concurrent dispatches are serialized: the second one sees the first one's result and is rejected if stock is insufficient. Schema `CHECK` constraints on `quantity` and `balance_after` are a second line of defense if application logic were ever bypassed.

Every ledger row stores `balance_before` and `balance_after`, so the ledger can be audited row by row without replaying it from the beginning.

## Idempotency keys

Each movement carries a UUID `request_id` (generated by the client, or by the server if omitted). The column is `UNIQUE`. A retry with the same ID and identical fields returns the original movement without changing stock. Reusing the ID with different fields returns 409, which catches client bugs instead of silently ignoring them.

## Opening stock

Creating an item with a positive quantity writes an `Opening stock` receive entry in the same transaction, so the ledger always explains the full balance.

## Immutable identity fields

SKU and unit cannot be edited. Changing a unit would change the meaning of every historical balance; a different unit is modeled as a new SKU. SKUs are stored uppercase and compared case-insensitively.

## Search and low-stock filtering

Search uses `instr(lower(column), lower(?))` over SKU, name, and location, so `%` and `_` are matched literally. An item is low on stock when `quantity <= reorder_level`. The summary counts low-stock and out-of-stock items in one aggregate query.

## Complexity

The ledger index `movements(item_id, id DESC)` makes per-item history reads proportional to the number of rows returned. Catalog listing is a full scan, which is appropriate for small local catalogs.
